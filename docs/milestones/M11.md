## What was built

Fourteen screens at `/ui/`, served by the same process that serves the API: overview, projects,
project detail, tasks, episodes, episode inspector, artifacts, retrieval, provenance, tools,
benchmarks, metrics, specialization, institutions, cost and events.

One HTML file, one script, one stylesheet. No build step, no framework, no CDN — and that is not
minimalism as taste. §6 forbids separate Colab logic and §33 makes Colab a first-class runtime; a
page that fetched a framework at load time would render differently, or not at all, in an
air-gapped or offline runtime. A test asserts that no served asset references an external origin.

Live updates ride §45's append-only event log over SSE. The log *is* the transport: each message
carries the event's `sequence` as its SSE id, so a reconnecting browser resumes with
`Last-Event-ID` and misses nothing. A stream keyed on timestamps would silently skip or repeat
rows that share a millisecond — the same reason `read_stream` orders by sequence. The stream is
deliberately bounded (25 s or 200 events) because `EventSource` reconnects on its own, and an
unbounded generator holds a worker and a connection open for a client that may already be gone.

## What the UI is actually for

Two rules that have governed the platform since M1 are properties of the *rendered page*, and
nothing before this milestone could check them:

**Absence is not zero** (ARCHITECTURE §3.9). `fmt.metric` is the only path a measured number takes
to the screen, and it cannot render `null` as `0`. A client that received `null` and printed
`0.0000` would satisfy every API test in the suite and still lie to every reader — an index of
0.0000 means "every profile performs identically", which is a finding; an absent index means
"there is not enough evidence to say".

**A failed gate withholds the result** (ARCHITECTURE §3.1). The benchmark screen renders the gates
first and, when one failed, says the metrics are withheld and why. The test seeds an experiment
run with a failed gate *and* metrics attached, and asserts the number never reaches the page.

Both are tested in a real browser, driving the real page against a real server. An assertion that
a route returns JSON is not evidence that a screen renders it.

## Defects found — all four are the same defect

Every one of these was found by opening the page in Chromium. None could have been found by the
API tests, which issue one request at a time.

1. **Every API read took SQLite's write lock.** The engine opens transactions with
   `BEGIN IMMEDIATE` so the job lease serialises the way `SELECT FOR UPDATE` does on PostgreSQL
   (§42) — but an immediate BEGIN takes the write lock *to read*. Two panels opening at once
   contended for a lock neither needed; the second waited out `busy_timeout` and failed with
   "database is locked". Fixed by giving safe methods a read-only session, which is what WAL is
   for: readers do not block the writer, unless you take the write lock to read.

2. **The event stream held a write lock for as long as a tab stayed open.** Same cause, worse
   consequence: a stream polling every half-second would block every agent in the workspace from
   writing. It now uses its own read-only factory — its own, not the request's, because the stream
   outlives the dependency's scope and a session held that long pins a PostgreSQL snapshot and
   blocks vacuum.

3. **Every authenticated read wrote `last_used_at` on the API key.** So the "read-only" session
   still had to upgrade to the write lock mid-transaction, which SQLite answers with SQLITE_BUSY
   rather than by waiting. Three fixes were tried and two failed, which is worth recording: a
   second session moved the contention without removing it, and bounding *that* session's lock
   wait does not work because `BEGIN IMMEDIATE` fires before any statement in the session, so the
   connection is blocked before a `busy_timeout` pragma can be issued — a 27-test module went from
   8 seconds to 9 minutes. The fix that worked was to stop writing on reads: usage is stamped only
   on requests that already write, coalesced to 60 s. The cost is stated in the function's own
   docstring rather than buried — for a key used only for reads, `last_used_at` reflects its last
   *writing* use.

4. **Two navigations in flight at once let the slower one win.** Rapid navigation left the screen
   you had left rendered over the one you asked for. Fixed with a render token: a render writes to
   the page only if it is still the current one.

The first three are one defect wearing three hats — *reading was writing* — and it was invisible
until something made three requests at once. That is what the browser test bought.

## Effect on the newcomer benchmark

**0.000, and expected.** Nothing here changes what an agent sees inside an episode: the UI reads,
and the read path now takes fewer locks than before. This is the fourth null recorded in this
project and the least interesting one; it is recorded because Part A asks for it every time.

The concurrency fixes do change something measurable, and it is worth stating in the direction the
evidence supports: before them, a browser with the event stream open and two panels loading could
make an agent's write fail with "database is locked" on the SQLite backend. After them it cannot,
because no read takes the write lock. That is a claim about contention, not about throughput, and
no throughput number is claimed here.
