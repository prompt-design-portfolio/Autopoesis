## The measurement: does technology actually accumulate?

§17 makes a claim that is easy to assert and easy to leave unmeasured:

> Later agents should discover and reuse good tools. [...] The civilization must accumulate
> technology, not just text.

Measured as a matched A/B over one variable — whether discovery is available. **Both arms can
build**; only `reuse` can find what an earlier generation built. Eight generations per arm.

**The mechanism works, in every condition:** `reuse` builds once and reuses 7 times; `rebuild`
builds all 8. Both arms solve the task every time, so this is a comparison of *cost*, not of
capability.

**The saving scales with what a tool costs to write**, which is the result that matters:

| tool size | reuse (tokens/episode) | rebuild (tokens/episode) | saved |
|---|---|---|---|
| 15 lines | 3 761 | 3 828 | **1.8%** |
| 35 lines | 3 761 | 5 414 | **30.5%** |
| 75 lines | 3 761 | 8 594 | **56.2%** |
| 165 lines | 3 761 | 15 774 | **76.2%** |

Reuse cost is **flat** in tool size — you do not pay to re-transmit what you do not rewrite —
while rebuild cost is linear in it. That divergence *is* what accumulating technology means, and
it is why a single measurement at one tool size would have said nothing: at fifteen lines the
saving is 1.8%, which rounds to nothing and would have supported the opposite conclusion.

Steady-state figures exclude generation 0, which has nothing to reuse in either arm. A mean over
all generations is dominated by that first episode and understates the regime a long-lived
collective actually operates in.

## A real defect the benchmark exposed: token accounting ignored tool arguments

The first run showed reuse costing **more** tokens than rebuilding. Chasing it found that
`count_tokens` was applied only to `message.content`, so a `create_tool` call carrying an entire
source file and test suite was billed **zero** prompt tokens.

The consequence is not cosmetic. §8's token budget is one of the bounds that makes an episode
bounded, and it was systematically under-counting exactly the behaviour it most needs to bound: an
agent that writes code puts that code in tool-call arguments. A tool-writing agent could exceed its
token budget by an unbounded margin without the budget noticing.

Fixed with `Provider.count_message_tokens` / `count_request_tokens`, which count content, tool-call
arguments *and* tool declarations. The pre-call budget check in `EpisodeRunner` uses the same
measure, so the check and the accounting cannot disagree. A test asserts a 4 000-character source
in a tool call costs over 900 tokens where it previously cost one.

An earlier version of the benchmark also mis-instrumented itself: it counted a *rebuild* as a reuse,
because "built" was keyed on creating the tool *definition* rather than writing a *version*. That
made the control arm look identical to the treatment, which is precisely the failure mode a control
exists to prevent.

## Design decisions inside the ecology

**A tool is untrusted code, always.** Validation runs the tool's tests in the sandbox, and so does
every later invocation. A test asserts that a tool attempting to open a socket during validation
is denied.

**A tool version cannot widen its own sandbox.** `permissions` may only *narrow* the granted
limits. Allowing it to widen would let a tool request the network by declaring it — the sandbox
granting privileges on the word of the code it is sandboxing. Tested with a tool that asks for
network access and 99 GB of memory; it gets neither.

**A tool that fails its tests is kept and stays discoverable.** "Someone already tried to build
this and it did not work" is exactly what a later toolmaker needs (§12), and deleting it guarantees
the attempt is repeated. It is registered `TESTS_FAILING`, ranks last in discovery, and carries
`MODEL_ASSERTION` provenance rather than `TOOL_OUTPUT` — a tool that fails its tests has not
verified anything.

**Untested is not failing.** Conflating them would let an untested tool inherit a tested one's
reputation. Discovery ranks passing above untested above failing, because untested *may* work and
nothing has checked, whereas failing has been checked and does not.

**A failing new version does not become current.** A bad edit degrades the collective's technology
by nothing: the previous working version stays in place, and the failing one is still recorded.
This also produced a bug the tests caught — a tool whose every version failed had no current
version and therefore reported as *untested* in discovery, outranking working tools. Discovery now
falls back to the latest version so a failing tool is visibly failing.

**A fresh tool is not a failing tool.** `success_rate` returns `None` for a tool that has never
run, not 0.0, so it does not rank below a broken one.

**Tool quality is measured, never declared.** `downstream_utility` is written only by credit
assignment (§A2.1); `success_rate` is a fold over real runs. An agent cannot claim its tool is
good.

## Effect on the newcomer benchmark

**None.** Advantage +0.300, reset removes 100%, scramble removes 100% — identical to M4 and M5.

Reported rather than omitted, and the reason is structural: the hidden-rule task family needs no
agent-written tool, because the probe it requires is built in. A tool ecology has nothing to
contribute to a task that does not call for a tool.

This is the second milestone in a row where the newcomer benchmark reported a null for a working
feature, and the pattern is now clear enough to act on: **that benchmark measures transmission,
and only transmission.** M9's benchmark families must include tasks whose difficulty comes from
needing capability that has to be *built*, or the capability-frontier measurement (§25) will keep
reporting nulls that mean nothing.
