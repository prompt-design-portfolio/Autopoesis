## The headline: the newcomer advantage survives a change of domain

M4 measured a newcomer advantage of **+0.300** on the hidden-rule device. Read strictly, that is a
result about *that device*. M10 makes it a result about the platform by running §22's procedure —
the same arms, the same gates, the same founder-free discipline, the same frozen configuration —
on a second domain that shares nothing with the first but the core.

| | hidden rule | code repair |
|---|---|---|
| what the answer is | one of ten opaque operation labels | a Python function the agent writes |
| how it is judged | string comparison | **executed in the hardened sandbox** against held-out checks |
| what a tool call buys | one probe of one (class, operation) pair | one candidate edit run on a worked example |
| agent policy | `PolicyAgentProvider` | `RepairPolicyAgentProvider` |
| budget | 7 tool calls / 10 operations | 5 tool calls / 6 candidate edits |
| **naive probe ceiling** | **0.500** | **0.500** |

The budgets differ so the *ceilings* match. Matching the ceiling rather than the raw budget is what
makes the two advantages comparable; matching the budget would have compared two difficulties and
called the difference a domain effect.

| arm | hidden rule | code repair |
|---|---|---|
| baseline_empty | 0.4667 | 0.5500 |
| **collective** | **0.7667** | **0.7500** |
| memory_reset | 0.4667 | 0.5500 |
| collective_scrambled | 0.4667 | 0.5000 |
| **newcomer advantage** | **+0.300** | **+0.200** |
| reset removes | 100% | 100% |
| scramble removes | 100% | 100% |
| mean probes, baseline → collective | 4.60 → 0.33 | 2.75 → 0.30 |

n = 30 (hidden rule, 5 seeds × 6 classes) and n = 20 (code repair, 5 seeds × 4 programs); three
accumulation passes per arm and seed; all four gates pass on both.

The advantage is smaller on code repair and that is the honest reading, not a rounding artifact:
the repair baseline starts higher (0.550 against 0.467) because six candidates at five calls is an
easier search than ten operations at seven, even at the same ceiling. What transfers is the
*shape* — the collective helps, resetting its memory removes all of the help, and scrambling
retrieval rank removes all of it too. On code repair `collective_scrambled` (0.500) falls **below**
baseline (0.550): reading two badly-ranked artifacts costs calls the agent would otherwise have
spent trying edits. That is the same sign M4 saw on the device and a stronger version of it.

## Why the procedure had to be refactored, and how the refactor was checked

A second copy of §22 for the second domain would have let the two drift, and the cross-domain
comparison would then be between two procedures rather than between two domains. So
`run_newcomer_benchmark` no longer implements §22 — it calls `run_newcomer_procedure(domain=...)`,
and so does `run_repair_benchmark`.

Refactoring a measuring instrument is only safe if the instrument still reads the same, so:
`scripts/newcomer_snapshot.py` runs one fixed configuration and prints the metrics. Run on the
tree at `11fb481` and on the refactored tree, the two outputs are **identical** — every arm, every
gate, the config hash — except one note string that now names the domain. That diff is the evidence
the refactor is behaviour-preserving; the M4 result stands unchanged.

## §5, §32 — a request becomes work, and the work survives the process

`civitas/services/projects.py`. `submit_request` turns *"investigate the cause of the intermittent
data corruption and produce a verified fix"* into a project, an objective, and four chained tasks
— investigate → hypothesise → verify → synthesise — linked by `TaskDependency`. §27's `ready_tasks`
already refuses blocked work, so the chain needed no scheduler change; the dependency rows are what
make it structural rather than advisory.

The decomposer is deterministic by default. A model-written decomposition is a set of model
assertions about what the work is, and if the decomposition varied run to run then no campaign over
it could be reproducible (§46). `ModelDecomposer` sits behind the same interface, and the project's
metadata records which produced the plan.

§32 asks for survival: *"Agent processes may die. Workers may restart. Colab sessions may terminate.
Projects must survive."* So the test destroys the process state — closes every session, disposes
every engine, builds a new engine from the same settings — and asks for the status again. The two
dictionaries are equal. `resume` is not a special code path; it is `next_ready_task` called again.

## The domain-adapter layer, and the leak rule it enforces

`civitas/domains/`. An adapter is four things the core genuinely cannot know: what a task says,
which tools act on it, who judges the answer, and what the stages of work are called. Everything
else — bounded episodes, arm enforcement, hybrid retrieval, credit assignment, the scheduler, the
experiment gate — is untouched.

§47 is easiest to violate exactly here, because the domain author writes both the description and
the evaluator spec, often in the same function. So the boundary enforces it: every domain declares
`hidden_terms` (strings that must not appear in agent-visible text at all) and `candidate_terms`
(the alternatives the answer must be indistinguishable among), and `check_no_leak` tests three
separate failures — a hidden term appearing verbatim, a marker word singling the answer out, and
the answer being presented differently from its alternatives, whether by **omission** or by
**frequency**. Presence-by-omission is the subtle one and the one an author introduces by accident.

The check runs in three places, not one: a parametrized test over *every registered domain*, the
`create_domain_task` funnel every benchmark task passes through, and the `civitas domain-tasks` CLI
command. It caught a real leak in this milestone — the code-repair description ended "call
submit_result with the corrected function source", and "the correct" is a marker.

## Defects found

1. **`try_patch` did not count a rejection as progress.** Every repair arm read 0.000 with the
   budget unspent: agents ruled three edits out, made no "progress", and died of `no_progress`.
   This is M4's defect #15 in a new domain, and it cost the same thing — a real result recorded as
   an agent failure. Fixed by setting `ctx.made_progress`, exactly as `probe_device` does.
2. **§A2.3 could never fire on code repair.** The duplicate index keys a documented failure on
   `(tool name, call arguments)`, and `try_patch` recorded `{"patch", "entry"}` while the call
   carried only `{"patch"}`. The key never matched, so `duplicate_failures` was structurally 0 —
   the same shape as M4's defect #14. Fixed by making `entry` a required call argument, which is
   also the correct fix rather than a convenient one: two functions in one workspace can be offered
   the same surface label, and a key without the entry would let a rejection for one block a good
   attempt on the other. `duplicate_failures` now reads 7 and 9 on the two collective arms.
3. **Two ambiguous patch anchors.** `"    return out\n"` also occurs inside
   `"        return out\n"`, so `flush_final_run` and `count_from_zero` silently edited a different
   line and stopped repairing anything. `Program.apply` now refuses an anchor that does not match
   exactly once. The first was caught by verifying the catalogue against its own worked examples;
   the second by the guard the first one motivated.
4. **The verification that caught (3) was itself too lax.** It treated a candidate that *raised* on
   application as simply "not the answer". A candidate that cannot be applied is not an
   alternative — it is a wasted tool call returning an error instead of evidence. The test now
   requires every candidate to apply cleanly.
5. **`ToolResult` has no `structured` field.** `try_patch` passed one, every call raised, and the
   runtime — correctly — swallowed it as a tool error rather than killing the episode. The episodes
   still ran, still cost budget, and read as agents that could not find a repair. A tool exception
   that degrades into a plausible-looking measurement is the failure mode this milestone kept
   producing.
6. **API writes emitted no events** (§45), and blind-arm suppression was recorded on
   `RetrievalDecision` but not returned on `RetrievalResult`. Both fixed while wiring the API.

## §50 — the API

26 routes plus four added here: `POST /workspaces/{id}/requests` (submit a high-level request and
get the plan), the project status and timeline endpoints, and `GET /domains`. Two disclosure rules
hold across all of them: `TaskOut` has no `evaluator_spec` field at all, and a cross-tenant id
returns **404, not 403** — a 403 confirms the id exists. `BenchmarkResultOut.metrics` is `None`
when gates failed, so a failed gate withholds the result over HTTP exactly as it does in process.

## The CLI

`pyproject.toml` has declared `civitas = "civitas.cli:main"` since M1 and the module did not exist.
It does now: `init-db`, `health`, `bootstrap`, `workspace`, `submit`, `status`, `timeline`,
`domains`, `domain-tasks`, `benchmark`, `manifest`, `serve`, `worker`. Each command is a few lines
over the same service function the API calls. Two disciplines are visible in the output: `init-db`
says *which* way it created the schema, because a schema built by `create_all` and one built by
migrations are not interchangeable; and `benchmark` prints the failed gates instead of a number
when a gate fails.

## Effect on the newcomer benchmark

Not a null this time. The domain layer produced a second, independent measurement of the same
effect: **+0.200 on code repair against +0.300 on the device, at a matched ceiling, with reset and
scramble each removing 100%.** M5, M6 and M7 each produced a null here for a working feature; the
instrument that answers "does this generalise" is the one M10 built.

The projects, API and CLI work does not move this number and is not expected to: none of it changes
what an agent sees inside an episode. What it changes is whether the platform can be *pointed at*
something — §65's remaining levels need exactly that.
