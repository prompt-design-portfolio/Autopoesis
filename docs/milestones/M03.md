## What was built

`civitas/runtime/` — providers, budgets, sandbox, tools, the episode runner.
`civitas/knowledge/` — arm policies, arm-enforced retrieval with `RetrievalDecision` logging,
duplicate-failure detection. `civitas/workers/` — the durable worker loop.

### Part B §4, enforced rather than requested

`EpisodeContext` is constructed inside `EpisodeRunner.run()` and dropped when it returns.
`EpisodeRunner` has no parameter through which a prior episode's state could arrive, `Episode` has
no column for reasoning, and `ModelCall` stores the accounting plus a request *hash* — never prompt
content, because a persisted transcript is a channel a UI, a retrieval or a replay tool could later
turn into inheritance.

`tests/test_state_isolation.py` drives two consecutive episodes **under every arm**. A canary in
episode 1's reasoning must appear in no environment-supplied input to episode 2. Both halves are
asserted: under `collective`, what episode 1 *externalised* does reach episode 2, and under `solo`
it does not. An isolation test that passed by making the collective inert would be testing the
wrong thing.

### Nine arms, machine-enforced (§21)

`civitas/knowledge/arms.py` turns each arm into a data structure retrieval reads. No prompt wording
can defeat it. Three decisions worth stating:

- **An unknown arm raises.** Falling back to `collective` would silently turn a mis-specified
  experiment into an unablated one, and the result would still look like evidence.
- **`collective_frozen` without a snapshot cut raises**, because without one it is
  indistinguishable from `collective` and would be reported as a control while being none.
- **Suppressions are recorded, not merely applied.** `RetrievalDecision.suppressed` lists what the
  arm removed and why. An ablation whose effect can only be inferred from an absence is not
  auditable.

### Duplicate-failure detection (Part A §A2.3)

Detection runs in **every** arm; only *surfacing* is arm-gated. That split is deliberate:
`duplicate_failure_rate` is a primary benchmark metric (§12, §48) and has to be comparable across
arms, so detection is the measurement and surfacing is the intervention. Conflating them would make
the metric unavailable in exactly the arms it exists to compare.

The hypothesis key is a sorted bag of content words plus the environment version, so a rewording
does not defeat the check — and a hypothesis that failed against one environment is not treated as
refuted against another (§15).

### Sandbox (§18) — and what it does not claim

Three backends: gVisor, Docker, and a POSIX-rlimit subprocess fallback for Colab, where containers
are unavailable. Every limit is driven by a test that would breach it: network denial, wall-clock
timeout killing the whole *process group* (killing only the direct child leaves a fork bomb's
children running), memory, process count, output truncation, and host-tree import denial via `-I`.

**The fallback is materially weaker and says so.** `isolation_level` is `PROCESS`, and that value
reaches the manifest. `get_sandbox` raises rather than downgrading when a requested backend is
unavailable: a silent downgrade would put a process-isolated result into a manifest claiming
container isolation, which is the confusion §46 exists to prevent.

### Secrets (§40)

The sandbox environment is an **allowlist**, not a denylist — a denylist over a process environment
guarantees the next unfamiliar variable gets through. `Settings.manifest_dict()` drops secrets by
*type* (`SecretStr`), so one added later cannot leak by being named something the filter does not
recognise. Tested by setting five differently-named credentials and asserting none reaches a
sandboxed process.

### Providers (§19)

All nine registered: Anthropic, OpenAI, OpenAI-compatible, Google, Hugging Face local, vLLM,
llama.cpp, plus deterministic and scripted. The network adapters are tested against a **mock
transport**, so the payload each vendor actually receives is asserted — a wrong field name is a
defect that otherwise only shows at the vendor.

`DeterministicProvider` is not only a test double. It is the scientific control for §20: with the
individual agent held *exactly* constant, a difference between arms cannot be sampling noise, which
a stochastic model can only establish statistically.

## Defects the tests found

1. **The isolation test's own confound.** The first version put the canary in episode 1's artifact
   *body* as well as its reasoning, then asserted it must not reach episode 2. That conflates two
   different things: an agent that writes something into an artifact has externalised it
   deliberately, and §4 requires that to reach later agents. Only what the agent merely *thought*
   must not survive. The test was wrong, not the runtime — and it would have passed only if the
   collective had been broken.
2. **A capture helper that counted the model's own output as input.** Assistant messages are echoed
   back within one episode; that is within-life state, which §4 permits and in fact requires.
   Counting it would have asserted that an agent cannot remember its own previous sentence.
3. **Unknown job kinds were retried.** `jobs.fail` decides retry-or-dead-letter from the attempt
   count, and the worker set the count *after* calling it. A missing handler is a deployment error,
   not a transient fault, so it now exhausts attempts first and dead-letters immediately.
4. **`preexec_fn` called `setsid` twice.** `Popen(start_new_session=True)` already does it; the
   second call raised and killed every sandboxed spawn. Also made each rlimit individually
   tolerant, so a platform refusing one limit does not abort the whole child.

## Metrics exposed

Per episode: tokens, prompt/completion split, tool calls, cost, model calls, wall time,
artifacts created/read/retrieved, duplicate failures, termination reason. Per retrieval: candidate
count, returned count, per-result feature vector, suppression list, latency. Per job: attempts,
lease history, outcome. These are the inputs the M4 benchmark consumes.

## Effect on the newcomer benchmark

Still not measurable — the benchmark is M4, which is next. What M3 establishes is that the
measurement will be *possible*: the arms are enforced, the model can be frozen exactly, and
credit-bearing reads are distinguished from retrievals.
