## The headline: the gate refused a change that did not help

§A2.2's requirement is that uncontrolled self-modification be *impossible by construction, not by
convention*. M8's demonstration puts two real proposals through the identical path under one
shared configuration hash and lets the gate decide.

| proposal | metric | treatment | control | gate |
|---|---|---|---|---|
| adopt hybrid retrieval | newcomer advantage | 0.4444 | 0.4444 | **REFUSED** |
| penalise only unproductive repeats (M7's correction) | task coverage | **0.8333** | 0.5000 | **APPROVED** |

Adoption rate 0.5. The retrieval policy remains at the built-in default; the scheduler policy is
now `productive_repeats v1`, with its approval evidence recorded.

The refusal is the part that matters. **A meta-learning mechanism that adopts every proposal is
not evaluating anything**, and the demonstration deliberately includes a proposal that does not
help so the refusal is exercised rather than assumed. It also closes the loop on M5: hybrid
retrieval was measurably worth something on rank quality, and measurably worth nothing on the
newcomer benchmark — and the gate, asked about the second, declines to adopt it. That is the
system correctly refusing to act on the wrong instrument.

## "Impossible by construction" — what actually enforces it

There is exactly **one** function the runtime uses to obtain a governed version, `gate.load_active`,
and it filters on `approved_by_experiment_run_id IS NOT NULL`, `status == "active"` and not rolled
back. A caller that wants an unapproved version cannot get one by asking differently.

`propose_policy` creates versions in `proposed` state, and nothing but `approve` moves them.
Proposal is deliberately unrestricted — §31 wants the collective to explore how it organises
cognition — but exploration takes effect only through measurement.

`load_active_body` falls back to the **built-in default**, not to the most recent proposal. That
distinction is load-bearing: falling back to the latest proposed version would let an unapproved
proposal take effect merely by existing, which is precisely the failure mode the gate exists to
prevent.

### What makes a comparison matched, checked rather than asserted

`check_matched` refuses on any of six grounds, each a way a comparison can look like evidence
without being it:

1. the runs belong to different experiments — no shared task family or budget;
2. treatment and control are the same arm;
3. **the configuration hashes differ** — the arms varied in more than the version under test;
4. either run has not completed;
5. **either run failed its gates** — a run that is not read (ARCHITECTURE §3.1) cannot support an
   approval either;
6. the metric is missing from one run, or the treatment did not improve it.

An approval resting on an unmatched comparison is worse than no approval, because it carries the
authority of evidence and nothing downstream re-checks it.

`run_matched_experiment` records **one** configuration hash for both arms rather than computing
one per arm: two independently computed hashes that happen to agree prove nothing about whether
the arms were actually matched.

### Reversibility (§60)

`roll_back` withdraws a version and restores its predecessor. Rolling back the only version
returns `None` and the runtime falls back to its default — the correct outcome rather than an
error, because the default is what the system shipped with and needs no approval.

A refused proposal is **kept**, in `proposed` state. A documented change that did not help is
exactly what stops the next agent proposing it again (§12).

## Reputation is multidimensional, and bounded (§29)

Eleven dimensions, each a different fold over outcome events, stored as append-only observations
so a reputation is always reconstructable from what produced it — the §A2.1 discipline.

§29 gives two requirements that pull against each other: trust *can* influence retrieval, and it
*must not* make dissent impossible. They are only compatible if the influence cannot outweigh the
evidence terms, so:

- `retrieval_influence` is capped at **0.25**, below both the provenance and validation weights —
  asserted by a test that computes a *perfect* reputation and checks it still cannot outrank
  evidence;
- only **confident** dimensions contribute, and confidence needs five observations: reputation
  earned on two episodes is an accident;
- influence is centred on 0.5, so an average reputation is neutral and a subject with no record is
  not penalised relative to one nobody has reason to distrust;
- a low-reputation artifact is ranked lower, never removed.

`confident_mean` exists for display and **nothing ranks on it**. §29 forbids collapsing trust into
one universal score; the aggregate is there so a dashboard can sort a list without any decision in
the system depending on the collapse.

Dimensions with no observations report `None` with a reason, never 0.0.

## Procedures are rules the runtime applies (§30)

§30's examples — *always reproduce this type of result before accepting it*, *tool X is unreliable
for input class Y* — are all rules, not advice. A procedure that only appears in a prompt is
indistinguishable from a suggestion, and §30 closes by asking whether an institution actually
improves outcomes, which cannot be answered about something the system does not enforce.

So a `Procedure` is a `trigger` and a `requirement`, both evaluated by the engine, and
`times_applied` counts real firings.

**A trigger the engine cannot evaluate is surfaced as a violation, not ignored.** A rule that never
fires while appearing active is worse than no rule, because the collective believes it is
protected.

**Only approved procedures apply.** Otherwise any episode could institute a rule for the whole
collective by writing one down.

`institution_effect` answers §30's closing question from the **matched approval evidence**, not
from a before/after on the live workspace. A before/after would confound the procedure with
everything else that changed while it was active, and would credit it for the collective simply
maturing.

## Effect on the newcomer benchmark

**None directly** — and this milestone is the first where that is the *right* answer rather than a
limitation. M8's mechanism is a gate on adoption; its effect on any benchmark is whatever the
adopted change does. The measurement that matters is the one above: two proposals, one adopted, one
refused, both decided on matched evidence.

The refusal is also the first time the newcomer benchmark's insensitivity has been *useful*: asked
whether hybrid retrieval improves it, the gate correctly answered no.
