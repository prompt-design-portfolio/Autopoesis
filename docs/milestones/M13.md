## Why an acceptance milestone exists at all

Every number in this project had already been measured. But M4 measured levels 1–3, M9 measured
4–6, and they ran at different commits under different configurations. **Six results produced by
six code versions are six claims.** The thing being accepted is one platform, so `civitas
acceptance` runs all six levels in one campaign under one manifest, gates each separately, and
reports a single verdict.

```
  PASS  L1 external knowledge usefulness             0.3   (success rate difference)
  PASS  L2 newcomer advantage                        0.3   (success rate difference)
  PASS  L3 ablation causality                        1.0   (fraction of the advantage removed)
  PASS  L4 distributed cognition                     0.35  (over the best single partition)
  PASS  L5 cumulative culture                        4     (generations reached)
  PASS  L6 collective capability growth              14    (hardest difficulty solved)

accepted: True
```

Five seeds, three accumulation passes, one code version, one sandbox description — including the
limit it **cannot** enforce here (`max_processes`), which is carried in the manifest so a run under
process isolation is never mistaken for one under kernel isolation.

One failing level fails the run. The levels are separate claims and an average over them would be
a number no claim supports.

## Levels 1 and 2 were the same number, and they are two claims

Through M9 both were reported as +0.300 from a single comparison. That conflated two things:

- **Level 1 — is external knowledge useful at all?** Hold the environment constant, vary sight:
  `collective` against **`solo_in_mature`**, a genuinely blinded agent facing the *same matured
  workspace*. This arm did not exist before M13.
- **Level 2 — does a newcomer benefit from what others built?** Hold the agent constant, vary the
  environment: `collective` against `baseline_empty`.

| arm | success rate |
|---|---|
| `collective` (mature workspace, can see it) | **0.767** |
| `solo_in_mature` (mature workspace, blinded) | 0.467 |
| `baseline_empty` (empty workspace) | 0.467 |

They still come to the same +0.300 — and **that identity is the finding, not a coincidence to
wave away.** A blinded agent in a rich workspace scores exactly what an agent in an empty one
scores. If arm blinding leaked at all, `solo_in_mature` would sit above `baseline_empty`; it does
not, to three decimals. This is the same internal-validity signal as `independent` tracking `solo`
in M9: the control that proves the instrument rather than the hypothesis.

The two levels can still come apart, which is why they are measured separately from now on. An
advantage at Level 2 with none at Level 1 would mean the matured workspace helps for some reason
other than its contents.

## Levels 4–6 had no gates until now

Levels 1–3 come from `BenchmarkResult`, which gates itself and raises rather than returning a
number when a prerequisite fails. Levels 4–6 came from three result classes that reported their
numbers unconditionally. That gap was invisible while each was read by a person who had just run
it, and would not have survived being read by anyone else.

They are gated now, and the gates state what each level needs in order to be *readable*:

| level | gate | what it prevents |
|---|---|---|
| 4 | `task_is_provably_unsolvable_alone` | a distributed-cognition result on a task that turned out to be individually solvable — evidence of nothing, discovered a campaign too late |
| 4 | `both_controls_ran` | "no single partition suffices" as an assertion rather than a measurement |
| 5 | `control_ran` | four generations of accumulation confused with four independent attempts |
| 5 | `chain_started` | a chain measured from a generation 1 nobody could solve |
| 6 | `controls_ran` | a frontier without `independent`, the check that repeated sampling buys nothing |
| 6 | `ladder_discriminates` | every arm reaching the same frontier, whatever the numbers say |

**The last gate fired on its first run.** `run_capability_frontier` defaults to a 0.75 success
threshold in M9's committed configuration but 0.5 in its signature, and at 0.5 every arm cleared
every difficulty. The gate refused to read the level rather than reporting a frontier of 14 for
solo, collective and independent alike. That is the gate discipline working on the milestone whose
job is to check the gate discipline.

## §64 — the production checklist, as code

A checklist in a document is a checklist nobody runs. `civitas preflight` is the same checklist
executable, exits non-zero on a deployment that is not ready, and reports **what is in force
rather than what is configured** — the two differ exactly where it matters:

```
  FAIL  every requested sandbox limit is enforced   NOT enforced here: ['max_processes']
  FAIL  jwt secret is set and not a placeholder     length 0
  WARN  database is postgresql                      SQLite serialises on its single writer
  WARN  sandbox provides kernel or container isolation   backend subprocess
```

It correctly refuses this development container, and for the right reasons. A warning is a
deployment that works and is worse than it could be; a failure blocks. Nothing reports "unknown"
quietly — a safety property that cannot be verified is not a satisfied one.

The sandbox check is the one that matters most, and it is the M4 finding made operational:
`RLIMIT_NPROC` is silently unenforced for uid 0, measured at 5000 processes against a limit of 8.
A bound the caller believes is in force but is not is worse than no bound, because it is relied
on.

## §63 — survival, tested by destroying the process

The notebook's acceptance cell has run this since M4. M13 makes it a test that runs in CI too: two
agents work, **every engine and session is destroyed**, a new engine is built from the file, and a
third fresh agent is asked to inherit what the first two left behind. Step 15 of §63 is "terminate
application/runtime"; a test cannot kill its own process, so it does the thing that actually
matters and checks the result rather than asserting it.

## Defects found

1. **`all([])` is `True`.** An acceptance report over zero levels would have reported
   `accepted: true` — a system accepted on the strength of running nothing, which is the most
   embarrassing possible pass. Now `accepted` requires at least one level.
2. **The frontier threshold defaulted to a value M9 had already measured as non-discriminating.**
   Caught by the gate rather than by reading the number.

## Effect on the newcomer benchmark

**+0.300, unchanged**, and now measured inside the acceptance campaign rather than beside it. The
`solo_in_mature` arm is additive — it neither changes what the other arms see nor what they score,
which the identical `baseline_empty` and `solo_in_mature` rates confirm.

## Where this leaves the project

M1–M13 are complete. Six scientific criteria pass under one manifest with their negative controls;
the platform runs the same code on SQLite and PostgreSQL, in Colab and in Kubernetes; and the
disciplines that made the numbers trustworthy — gates precede rows, absence is not zero, matched
comparisons, founder-free measurement, the `π` rotation — are enforced by code and tests rather
than by care.

Two limitations are worth carrying forward rather than leaving to be rediscovered. **The agents
are deterministic policies, not language models**: that is the strongest available instrument for
measuring the *platform's* contribution (§20), and it is not a measurement of what a model would
do. And **two domains is two**: the transfer result in M10 shows the machinery is not specific to
one device, and it does not show it is general.
